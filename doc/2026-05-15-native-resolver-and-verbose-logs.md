# Native Resolver And Verbose Logs Design

## Purpose

Lee Codex should use native OpenAI-compatible Chat Completions tool calling as its default agent protocol. The earlier custom JSON action protocol made the model place tool intent in assistant text, which was brittle and hid important provider response fields such as `tool_calls`, `finish_reason`, `refusal`, and `content: null`.

The new design keeps the agent loop small, but moves action extraction behind an internal resolver strategy. Version 1 ships only the native Chat Completions resolver. JSON-schema or Responses API resolvers can be added later without changing workspace tool execution.

## API Surface

Version 1 targets Chat Completions because it is the broadest OpenAI-compatible surface across OpenRouter and other providers.

The provider request must use native tool calling fields:

- `messages`: OpenAI-compatible conversation messages.
- `tools`: function tool definitions for `list_files`, `read_file`, `write_file`, and `run_command`.
- `tool_choice: "auto"`: the model may call tools or answer normally.
- `parallel_tool_calls: false`: request sequential tool behavior for v1.

The resolver must handle assistant messages according to the OpenAI Chat Completions shape:

- Final answer: assistant `content` is a string and `tool_calls` is absent, `null`, or empty.
- Tool request: assistant `tool_calls` contains one or more function calls. `content` may be `null`.
- Each function call has an `id`, `type: "function"`, `function.name`, and JSON-encoded `function.arguments`.
- Each tool result is appended as a `role: "tool"` message with the matching `tool_call_id`.

OpenAI documents that function call arguments are JSON generated by the model and must still be validated by application code. OpenRouter documents a compatible `tools` and `tool_choice` interface and provider routing controls.

Reference docs:

- OpenAI Chat Completions: https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create
- OpenAI function calling: https://platform.openai.com/docs/guides/function-calling?api-mode=chat
- OpenRouter tool calling: https://openrouter.ai/docs/guides/features/tool-calling
- OpenRouter API request schema: https://openrouter.ai/docs/api/reference/overview

## Resolver Behavior

The resolver strategy interface should convert one provider response into a deterministic agent step:

- `final`: a final assistant message to show the user.
- `tool_calls`: one or more executable tool calls plus the original assistant message to preserve in conversation history.
- `failed`: an unrecoverable resolver error.

Native resolver rules:

- Treat plain assistant content as the final response.
- Treat tool calls as tool work even when assistant content is also present; verbose output still prints that content.
- Execute multiple tool calls sequentially in array order.
- Parse each `function.arguments` string as JSON.
- If arguments are malformed but the tool call has a valid `id`, append a tool error message for that `tool_call_id` and continue the loop.
- If a tool call is missing a usable `id`, has an unsupported `type`, or lacks a valid function name, fail the turn clearly.
- Unknown tool names remain recoverable workspace tool errors when the call shape is valid.
- No automatic fallback to JSON-schema mode.

## Provider Behavior

The OpenAI-compatible provider client must preserve raw provider details instead of flattening the response to a string. It should return:

- The first assistant `message`.
- The first choice `finish_reason`.
- The raw provider response.

OpenRouter requests should also include:

```json
{
  "reasoning": {
    "effort": "none",
    "exclude": true
  },
  "provider": {
    "require_parameters": true
  }
}
```

`require_parameters` prevents routing to providers that would ignore native tool-calling parameters. Reasoning suppression prevents reasoning-only responses from replacing the assistant content/tool-call payload.

## Verbose Logging

Verbose mode is a debugging mode. It should be more explicit than default output and should create a local conversation log.

Generated log files live under `/log` and are ignored by git:

- Commit `log/.gitkeep`.
- Ignore `log/*.json`.
- Do not redact by default. These files can contain prompts, file contents, command output, and tool arguments.

Each verbose single-shot run gets one JSON log file. Each verbose interactive session also gets one JSON log file that grows across user turns.

The log file is an envelope:

```json
{
  "version": 1,
  "startedAt": "2026-05-15T00:00:00.000Z",
  "updatedAt": "2026-05-15T00:00:01.000Z",
  "status": "running",
  "provider": "openrouter",
  "model": "openai/gpt-oss-120b:free",
  "cwd": "/workspace",
  "messages": [],
  "events": []
}
```

`messages` is the exact OpenAI-compatible message array for replay and inspection. `events` contains raw assistant responses, tool results, resolver errors, and status changes.

Verbose terminal output should use stable ANSI colors:

- Assistant content: cyan.
- Tool calls: yellow.
- Successful tool result: green.
- Tool errors and resolver errors: red.
- Raw metadata: dim.

Verbose output must always print assistant `content`, including `null`, and must always print the model's requested tool calls before execution.

## Non-Goals

- Public `--resolver` flag.
- Automatic fallback to JSON-schema mode.
- Streaming.
- Responses API migration.
- Parallel tool execution.
